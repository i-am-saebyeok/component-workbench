# 서비스 용도와 BDD 작성

이 폴더에는 이 서비스 컴포넌트의 실제 용도·선택 조건·기대 동작을 기록합니다. 기본 컴포넌트나 예제 기능은 등록되어 있지 않습니다. catalog의 bdd 목록에는 docs_root 기준 `.feature` 상대 경로를 연결합니다.

## 시나리오에 담을 것

- Given: 사용자의 상황과 이미 성립한 조건을 적습니다.
- When: 컴포넌트나 variant를 선택·사용하는 구체적인 행동을 적습니다.
- Then: 사용자가 확인할 수 있는 결과를 적습니다.
- 필요한 경우 금지 사용·실패/빈 상태·variant가 바꾸는 점과 바꾸지 않는 점을 구분합니다.

형식은 Feature·Scenario 또는 Scenario Outline·Given/When/Then을 사용하고 시나리오에 안정적인 태그를 붙입니다. 코드나 JSON 값을 그대로 복사한 설명보다 “어떤 상황에서 왜 이 컴포넌트를 고르는가”를 드러냅니다. 관련 컴포넌트/variant ID는 실제 catalog와 일치시킵니다.

영어 Gherkin 키워드를 사용합니다. 각 Scenario/Outline 바로 위에 서비스 안에서 고유한 `@태그`를 하나 이상 붙이고 단계를 작성합니다. Outline에는 Examples가 필요합니다. 태그에서 컴포넌트나 variant의 의미를 자동 추론하지 않습니다.

문서 연결의 원본은 component의 bdd 파일 참조입니다. 도구는 참조 파일·일반 Gherkin 구조·시나리오의 고유 안정 태그를 확인합니다. 태그 이름의 namespace를 강제하거나 본문에서 component/variant의 의미를 자동 추론하는 검증이 아닙니다. 의미가 맞는지는 서비스 작성자와 실제 유스케이스 검사에서 대조합니다.

## 읽기와 검증

웹 문서 패널과 MCP get_component/resources는 경로뿐 아니라 이 본문을 제공하는 계약입니다. AI가 사용 의도와 피해야 할 조건을 읽고 선택할 수 있게 작성합니다. 아직 없는 제품 기능·물성·업무 규칙을 구현됐다고 설명하지 않습니다.

파일이나 태그가 있다는 사실은 시나리오 실행 성공이 아닙니다. 서비스의 실제 동작 검증과 안정 ID를 연결하고 무엇을 실행했는지 별도 결과에 기록합니다. 정의·variant·문서 참조·시나리오가 어긋나면 함께 고칩니다. BDD 변경은 원본 fingerprint에 영향을 주므로 기존 선택/recipe의 원본과 구분합니다.
